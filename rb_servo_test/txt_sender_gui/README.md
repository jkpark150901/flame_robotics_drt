# Motion TXT 전송 GUI

프로젝트 루트에서 실행:

```bash
python rb_servo_test/txt_sender_gui/app.py
```

Python 표준 라이브러리와 tkinter만 사용합니다. tkinter가 없는 Ubuntu에서는 `sudo apt install python3-tk`가 필요합니다.

1. **TXT 열기**로 `rb_servo_test/joint_only_motion/motion_txt/r1_RT/` 또는 `r2_DDA/`의 파일을 선택합니다. Servo J 20·30·40ms와 JB2 blending 0·50·100 파일을 지원합니다.
2. 연결할 서버 IP / Host와 Port(기본 5000)를 입력합니다. 반복 1은 한 번, 0은 무한 반복입니다. 파일의 LOOP 시작 표식을 기준으로 setup은 첫 실행에서만 전송합니다.
3. 미리보기에서 파일과 자동 인식한 Servo 주기를 확인하고 **연결 후 전송**을 누릅니다. 별도 모드 전환 명령은 보내지 않으며 현재 서버/로봇 모드로 동작합니다.
4. 전송 종료 후 **전송 시간 CSV 저장**으로 계획 시각, 실제 소켓 전송 시각, 지연, 실제 지령 간격을 저장할 수 있습니다. 시각은 단조 시계 기준이며 로봇 수신 시각이나 실측 동작 시각이 아닙니다.

## 전송 순서와 주기

- 명령 본문은 바꾸지 않고 UTF-8로 인코딩한 뒤 선택한 LF/CRLF 끝 문자를 붙입니다. 주석은 서버에 보내지 않습니다.
- `# WAIT 1 s after completion.`은 로컬 1초 대기로 해석합니다. `wait (1.0 sec)`도 로컬 대기로 처리합니다. 그 외 설명 주석은 건너뜁니다.
- Move J, `move_finish_wait()`, JB2 clear/add/run 등 일반 명령은 각각 `The command was executed` 응답을 받은 뒤 진행합니다. 따라서 setup Move J와 완료 대기 응답 이후에 Servo의 주기 타이머가 시작됩니다. 서버는 로봇의 완료/거부 응답을 그대로 전달해야 합니다. 중간 서버가 임의로 조기 ACK를 반환하면 실제 완료를 보장할 수 없습니다.
- Servo J는 각 명령의 `t1`을 주기로 읽고 `perf_counter()`의 절대 시각으로 예약합니다. 응답 수신은 병행하므로 각 Servo 명령 응답을 기다리느라 주기가 늘어나지 않습니다. 연속 Servo 전송을 마친 뒤에는 마지막 t1과 누적 응답을 기다린 후 후속 완료 대기 명령을 보냅니다.
- 응답을 버리지 않고 FIFO 개수로 추적하므로 이전 Servo 응답을 후속 완료 대기 응답으로 잘못 소비하지 않습니다. 분할되거나 여러 개가 합쳐진 ACK 토큰도 처리합니다. 각 명령에 ACK 1개가 반환되는 서버와 전용 연결이 필요합니다.
- Servo TXT에 포함된 반복 목표가 이미 대기 시간입니다. Servo 구간에 별도 대기를 추가하지 않습니다.
- 허용 지연 기본값은 10ms이며 실제 적용 상한은 `min(설정값, 현재 t1의 절반)`입니다. OS 또는 소켓 전송이 이를 넘기면 후속 전송을 중단합니다. 밀린 지령을 몰아서 보내거나 누락해서 따라잡지 않습니다. 일반 OS와 TCP이므로 하드 실시간 전송은 보장하지 않습니다.
- 오류/거부 응답, 연결 종료, 응답 제한 시간 초과 시 후속 전송을 중단합니다. **후속 전송 중단**과 창 닫기는 이미 실행 중인 로봇 모션을 정지하는 기능이 아닙니다.

기본 응답 제한은 120초입니다. 이 GUI는 상태 포트 5001을 조회하지 않으며 로봇의 실제 위치·도달을 별도로 검증하지 않습니다.

## 로컬 검증

```bash
python -m unittest discover -s rb_servo_test/txt_sender_gui -v
```

로컬 TCP 모의 서버로 setup 완료 대기, Servo 주기, 분할/병합 ACK, 지연 ACK, JB2의 시간 대기, setup 1회 반복, 취소, 오류/타임아웃/접속 종료, 지연 초과 중단을 검증합니다. 실제 로봇 연결은 하지 않습니다.
